# AI 执行规范 · 审美方向 · 人机协作协议

> 目的：避免“用户说 A，AI 问半天后做成 B；用户 review 发现很丑/信息密度差；无限返工”的循环。以后所有分享型 HTML / Deck / Boss Deck 项目，先按本协议锁定方向，再执行。

---

## 0. 总原则

AI 不应该一上来就开始写页面。

正确顺序是：

```text
定义用户 → 定义目标 → 定义 takeaway → 定义画风 → 定义页面类型 → 定义素材 → 再执行
```

如果前面没有定义清楚，后面执行越快，返工越多。

---

## 1. 开工前必须回答的 7 个问题

### Q1. 这次分享的用户是谁？
不是泛泛的“观众”，必须明确：

- 老板 / 决策者？
- 同事 / 执行团队？
- AI Builder 社区？
- 技术同学？
- 业务方？
- 初学者？

不同用户决定不同表达方式：

| 用户 | 需要看到什么 | 不需要什么 |
|------|--------------|------------|
| 老板 | ROI、资源、风险、决策点 | 技术细节堆叠 |
| 同事 | 怎么开始、怎么复用、材料在哪里 | 太抽象的方法论 |
| 技术同学 | 架构、模块、接口、Evals | 过度包装 |
| 社区分享 | 真实过程、wow moment、方法路径 | 内部政治细节 |
| 初学者 | 最小闭环、步骤、示例 | 太复杂的系统图 |

---

### Q2. 观众听完后要带走什么？
必须提前定义 takeaway。否则页面会变成“我做了很多东西”的堆叠。

Takeaway 分三层：

1. **认知 takeaway**：观众相信了什么？
2. **方法 takeaway**：观众知道怎么开始吗？
3. **资源 takeaway**：观众能拿走什么文件/链接/框架？

模板：

```text
这场分享结束后，观众至少应该带走：
1. 一个核心判断：________
2. 一个可复用框架：________
3. 一个可立即尝试的起步路径：________
4. 一个资源入口：________
```

---

### Q3. 这次的画风是什么？
不能边做边试。先选 style preset。

当前 sharing deck 的基准水准：

- 米白背景 + 橙/青强调
- Plus Jakarta Sans + DM Mono
- 大圆角卡片
- 真实截图 + 浏览器框/手机框
- 深色重点面板
- 标签 pill
- tab 切换大图
- 信息密度高但不堆字

以后如果没有明确要求，默认使用 **Warm Builder** 风格，不要降级成普通 PPT 风。

---

### Q4. 每页是什么类型？
每页先归类，再设计。

| 类型 | 目标 | 推荐模板 |
|------|------|----------|
| 证据页 | 证明“真的做了” | 大图 / tab / asset wall |
| 方法页 | 让人知道怎么做 | 左概念右案例 / 对比卡 |
| 流程页 | 展示步骤和依赖 | pipeline / timeline |
| 决策页 | 推动选择 | option cards / ROI / risk |
| 故事页 | 建立记忆点 | 时间线 + 原话 |
| 资源页 | 带走内容 | resource cards + QR/link |

禁止：没有归类就直接排版。

---

### Q5. 每页的视觉证据是什么？
每页都要问：

```text
这页靠什么证明？
```

如果答案是“靠文字解释”，这页大概率不够好。

优先级：

```text
真实截图 > 可运行链接 > 真实数据 > 流程图 > 结构图 > 文字说明
```

---

### Q6. 哪些内容必须原文保留？
用户给出的原话，有些不是素材，是“语感锚点”。不能擅自改成通用表达。

例如：
- “悬而未决时的判断力”
- “外星工具”
- “Wow Moment”
- “锯齿时刻”
- “探索、上头、冷静、稳定期”

规则：
- 用户明确给出的金句，优先原文保留；
- 如需压缩，只做轻微编辑；
- 不要改成平庸的咨询腔。

---

### Q7. 哪些地方不能自作主张？
高风险项必须先确认：

- 删除用户提过的页面/素材；
- 改页面顺序；
- 改主叙事；
- 替换用户原话；
- 把截图换成模拟图；
- 把用户要求 A 解释成 B；
- 改风格体系。

## 2. AI 执行协议

### 2.1 用户说 A，就先执行 A

不允许：
- 过度联想；
- 自己扩展到 B/C/D；
- 为了“更完整”改掉用户明确说的部分。

正确动作：

```text
1. 复述 A 的可执行版本；
2. 如果 A 有歧义，只问一个问题；
3. 如果 A 足够明确，直接改；
4. 改完报告 commit + 链接。
```

---

### 2.2 不要让用户反复 review 低级问题

AI 必须自己检查：

- 字是不是太多；
- 图是不是裁切；
- 图片是不是太大/太小；
- tab 顺序是否和用户要求一致；
- 有没有误删；
- 有没有视觉很丑；
- 是否保持现有风格水准；
- 是否提交了临时文件。

用户 review 应该看“方向和判断”，不应该帮 AI 找低级 bug。

---

### 2.3 每次改动必须绑定 evidence

完成汇报至少包含：

```text
改了什么
在哪一页
为什么这样改
commit hash
Vercel 链接
```

如果做的是视觉改动，必须说明图像处理方式：

```text
cover / contain / scrollable
max-width 多少
是否支持上下滚动
```

---

### 2.4 执行边界

AI 可以主动：
- 修显然的错别字；
- 调整图片缩放；
- 修 HTML/CSS bug；
- 补 `.gitignore`；
- 做 repo hygiene；
- 生成设计规范文档。

AI 不应主动：
- 删除用户提过的素材；
- 改用户原话的核心语气；
- 换整体画风；
- 把用户指定顺序改成“我觉得更好”的顺序；
- 把真实证据替换成 mock。

## 3. 审美方向规范

### 3.1 当前 sharing deck 的审美基准

这套风格已经被用户认可，后续不要降级。

关键词：

```text
Warm Builder
真实
高级但不冷
信息密度高
产品感
系统感
证据感
不是模板 PPT
```

视觉元素：
- 米白/暖灰背景；
- 橙色作为主强调；
- 青色作为系统/协作强调；
- 大圆角；
- 柔和阴影；
- 深色面板承载重点；
- mono 字体做标签；
- tab 切换大图；
- 截图要能看清；
- 资源页要像产品卡片。

---

### 3.2 禁止的审美退化

- 纯白底 + 普通蓝色按钮；
- 默认网页卡片风；
- 截图小到看不清；
- 文字堆满页面；
- 没有视觉锚点；
- 三栏平均塞图；
- 过度花哨动画；
- 右侧/底部复杂导航；
- 过多水印和重复标签。

---

### 3.3 图片模式默认规则

| 图片类型 | 默认模式 |
|----------|----------|
| 横向 PPT / HTML 截图 | cover 或 contain，看是否裁切重点 |
| Dashboard / 长页面 | scrollable + max-width 85-90% |
| 手机 App 长图 | scrollable + max-width 60-85% |
| 书页 / 多页文档 | scrollable + 多图拼接 |
| Agent 架构图 | scrollable/contain，保证整体可见 |
| 视频 | autoplay muted loop |

## 4. 人机协作协议

### 4.1 用户负责什么

用户负责：
- 真实判断；
- 哪些内容重要；
- 哪些词有语感；
- 观众是谁；
- 什么程度算“好看”；
- 哪些资源可公开。

### 4.2 AI 负责什么

AI 负责：
- 结构化需求；
- 快速生成版本；
- 维护 repo；
- 检查样式一致性；
- 提前发现风险；
- 把用户原话沉淀成规范；
- 不让用户重复说同一件事。

---

### 4.3 正确循环

```text
用户：给方向 / 原话 / 约束
AI：整理成执行 checklist
用户：确认或补一句
AI：小步实现 + 自检 + push
用户：review 高阶判断
AI：沉淀成规范
```

错误循环：

```text
用户：说 A
AI：猜成 B
AI：做很久
用户：发现丑/错/信息差
AI：返工
重复
```

## 5. 开工模板

以后新分享项目启动时，AI 必须先输出：

```md
# Project Brief

## 用户
这次观众是谁？

## 目标
这场分享要让他们相信什么？

## Takeaway
1. 认知 takeaway：
2. 方法 takeaway：
3. 资源 takeaway：

## 画风
Style preset：Warm Builder / Executive Dark / Clean SaaS / ...
参考页面：
禁用风格：

## 页面结构
P01 ...
P02 ...

## 素材
已有：
缺口：

## 执行边界
哪些可以 AI 自主改：
哪些必须问用户：
```

没有 Project Brief，不进入 HTML 编写。

---

## 6. 必须记住的红线

1. 不要忘记用户已经说过的话。
2. 不要用户说 A，AI 做 B。
3. 不要用低审美模板糊弄。
4. 不要把讲稿灌成字墙。
5. 不要让用户反复指出同一个问题。
6. 不要提交临时文件污染远端。
7. 不要每次重新发明风格。
8. 不要丢掉用户原话里的语感。
