## 2.1 n8n 肌肉：流程真的能跑起来

### 讲稿

第一块肌肉是 n8n。

大家可以先把 n8n 理解成一个自动化总机。

它不一定负责所有思考，但它负责在正确时间，把正确信息送到正确系统。

比如一个最小闭环：

任务状态变化了，触发 workflow；
workflow 去 Airtable 读取状态；
Code 节点判断下一步是提醒、等待还是升级；
然后推送到飞书或微信；
最后同步到 Dashboard。

这件事的价值不是“我会拖节点”。

真正的价值是：AI 的输出不再停留在聊天框里，而是进入任务状态、提醒、看板和复盘。

这就是从“一次性回答”到“运营闭环”的变化。

### 可展示素材

优先展示 workflow：

- `01-overdue-reminder.json`：逾期任务提醒
- `02-eod-feishu.json`：EOD 飞书汇总
- `03-dashboard-sync.json`：Dashboard 同步
- `06-sharing-tracker.json`：分享项目跟踪

可以展示：

- workflow JSON 文件名
- 节点流：Trigger → Airtable → Code Decision → Feishu Push → Dashboard
- Remotion n8n pipeline prototype
- Dashboard / Airtable 状态页（如果能截）

### 专业概念

Workflow automation：把一连串任务按触发条件、数据流和动作规则自动执行。

n8n 里的核心概念可以用四个词解释：

- Trigger：什么时候开始。
- Data / State：读取什么状态。
- Logic：怎么判断下一步。
- Action：把结果推到哪里。

### 费曼解释

如果把公司日常工作比作一个办公室，n8n 就像一个自动化调度员。

它看到某个事件发生，比如任务逾期，就去表格里查状态；
查完之后判断要不要提醒；
需要提醒就发给对应的人；
发完再把看板更新。

它不是万能大脑，但它能让信息按规则流动起来。

### 优势

1. 把 AI 产出接进真实工具链。
2. 让任务状态自动流转，而不是靠人记。
3. 可以连接 Airtable、Feishu、Dashboard、GitHub、Webhook。
4. 可以把“判断”放在 Code 节点或 AI 节点里。

### 我的设置

- Airtable：任务状态源。
- n8n：workflow 编排。
- Feishu / WeChat：提醒和通知。
- Dashboard：状态可视化。
- GitHub：保存 workflow JSON / 项目产物。

### 我的踩坑

1. Credential 和权限最容易卡。
2. workflow 多了以后，如果没有命名规范，很快会乱。
3. 一开始不要追求全自动，关键节点先 human confirm。
4. 没有失败路径和日志，自动化坏了也不知道。

### 特别 Tips

- n8n workflow 可以让 AI 直接写 JSON，再导入 n8n 微调。
- Code 节点可以承担复杂判断，不必所有逻辑都拖节点。
- 每个 workflow 最好有失败路径。
- 最小闭环比宏大自动化更重要。

### 金句

- Agent 输出如果不能进入运营闭环，就只是一次性聊天。
- n8n 让 AI 输出进入真实管理系统。
- 不要一开始追求全自动，先让状态可流转、可观察、可确认。

## 2.2 Copilot + Skill 肌肉：从想法到高质量产物

### 讲稿

第二块肌肉是 Copilot / Codex 加 Skills。

这里我不想只展示“AI 写代码”。

因为写几行代码其实不是最难的。

更难的是：一个复杂想法，能不能被推进成结构清楚、审美在线、可以展示、可以交付的资产。

比如这次分享本身就是一个例子。

从一开始只是一个方向：我想讲 AI 工作系统。

然后它被拆成：

- 演讲定位
- 稿件素材框架
- V4 / V5 演讲稿
- HTML deck
- 开场视频 concept
- 视频 HTML base
- Remotion pipeline prototype
- GitHub commit
- Project State

这里面有代码，也有内容，也有审美，也有项目管理。

所以我更想表达的是：Copilot + Skill 不只是帮我写代码，而是帮我把复杂审美、内容结构和产品表达推进成可交付资产。

### 可展示素材

重点展示：

- 我的 PPT / 演示稿页面
- AutoStackSharing 主 HTML
- 之前仓库中的其他高审美 HTML 页面 / 产品页 / 课件页
- `SPEECH_SCRIPT_V4_20260513.md`
- `PRESENTATION_RUN_OF_SHOW_V1_20260513.md`
- `HTML_DESIGN_OPTIMIZATION_V1_20260513.md`
- `VIDEO_OPENING_MUSCLE_CONCEPT_V1_20260513.md`
- `OPENING_VIDEO_MATERIAL_MAP_V1_20260513.md`
- GitHub commits

### 为什么 PPT / HTML 很重要

这里有一个很难一句话解释的壁垒：审美和表达质量。

很多人以为 AI 做 HTML，就是生成一个页面。

但真正难的是：

- 信息密度不能降。
- 结构要清楚。
- 视觉要高级。
- 不能像模板套壳。
- 要能承载复杂业务内容。
- 要能在演讲、视频、截图里复用。

所以展示 PPT 和 HTML，本质是在展示“AI + Skill 能不能承接复杂表达任务”。

### 专业概念

Skill 可以理解为 reusable capability，也就是可复用能力模块。

它和 prompt 不一样。

Prompt 更像一句临时指令；Skill 更像一套做事方法。

一个好的 Skill 不只告诉 AI “做什么”，还会定义：

- 什么时候用
- 输入是什么
- 参考什么
- 步骤是什么
- 输出标准是什么
- 怎么检查
- 哪些坑要避开

### 费曼解释

如果 prompt 是你临时对同事说一句：“帮我做个 PPT。”

Skill 就像你已经沉淀好一份 SOP：

什么场景要做 PPT，先问哪些问题，用什么视觉规范，怎么组织页面，怎么检查信息密度，怎么输出，怎么复盘。

所以 Skill 的价值不是让 AI 更会聊天，而是让 AI 做事更稳定。

### AI 编程流程

我现在更倾向于让 AI 先写 plan，而不是直接写代码。

这和一些 AI coding 最佳实践一致：先把背景、架构、约束、验收标准说清楚，让 AI 先给方案和任务拆解，再进入实现。

我的流程是：

Spec → Plan → Build → Test → Review → Ship

也就是：

1. 先定义问题。
2. 再拆实现方案。
3. 再生成代码或页面。
4. 再测试 / 截图 / 渲染 / build。
5. 再 review 是否符合目标。
6. 最后 commit / push / 同步状态。

### 我的 Skill 体系例子

这次分享可以串很多 Skill：

- PLO：判断任务类型和路线。
- frontend-slides：生成 HTML 演讲页。
- ai-video-production-pack：组织视频生产。
- writing-book：沉淀长文和知识资产。
- airtable-dashboard：同步任务状态。
- interaction-self-reflection：复盘交互质量。
- model-router：不同模型做不同任务。
- grill-me：拷打方案和逻辑。

这不是一个 Skill 单点调用，而是十几个 Skill 串成一套内容和产品生产系统。

### 我的踩坑

1. Skill 太多会变成“技能垃圾堆”。
2. 如果不绑定真实产物，Skill 只是说明书。
3. 如果不记录反馈，Skill 不会变好。
4. 如果让 Skill 自动乱改自己，会失控。
5. 视觉类任务不能只看“生成了没有”，要看审美、信息密度、可讲性。

### 特别 Tips

- 做三次以上的任务再 Skill 化。
- Skill 可以串联成 pipeline。
- Skill 可以自进化，但要先记录、再 dry-run、最后 human confirm。
- 对高审美任务，要把视觉参考库和输出标准写进 Skill。
- AI coding 不要一上来写代码，先要 plan 和验收标准。

### 金句

- Prompt 是一次性的，Skill 是可复用的。
- 真正的效率来自能力模块化，而不是每次重新问一遍。
- AI 不只是写一段代码，它能把复杂审美、内容结构和产品表达推进成可交付资产。

## 2.3 Agent 搭建肌肉：一个人背后有一个小团队

### 讲稿

第三块肌肉是 Agent 搭建。

很多人说 multi-agent，会想到开很多聊天窗口。

但我理解的 Agent OS，不是窗口数量，而是协作机制。

在我的系统里，有几个角色：

- SAM：主脑，负责全局协调和升级处理。
- Andrew：学习、研究、技术评估。
- Rex：工作项目、工程推进。
- Lulu：内容、写作、设计、视频。
- Alex：个人节奏和生活支持。

这些名字不是重点。

重点是它们背后的机制：

- SOUL.md：角色和边界。
- AGENTS.md：工作协议。
- HEARTBEAT.md：主动巡检。
- memory：长期记忆。
- agent_tasks：任务账本。
- PROJECT_STATE：长项目状态。

这意味着一个任务不是问完就结束。

它可以被记录、分配、追踪、升级、复盘，也可以在几天后继续接上。

### 专业概念

AI agent 可以理解为：有目标、有工具、有记忆、有执行循环的 AI 系统。

它和普通聊天机器人不一样。

聊天机器人主要回答问题；Agent 需要根据目标选择工具、执行步骤、观察结果、继续下一步。

Multi-agent system 不是“很多 AI 一起聊天”，而是多个角色围绕任务分工协作。

### 费曼解释

单个 AI 像一个聪明实习生。

Agent OS 像是你给多个实习生安排了角色、任务表、工作记录、例会机制和主管。

没有这些机制，多几个实习生只会更乱。

有了这些机制，它们才能围绕真实项目持续工作。

### 我的设置

- SAM：L3 主脑，全局协调。
- Andrew / Rex / Lulu / Alex：L2 专业 Agent。
- 每个 Agent 有 SOUL / AGENTS / HEARTBEAT。
- 长任务写入 Project State。
- 关键进度写 memory。
- 任务状态写 agent_tasks。
- 重要产物推 GitHub。
- 状态最好同步 Dashboard / Airtable。

### MAE + 可视化

下一步更重要的是 MAE：Multi-Agent Execution。

也就是多个 Agent 不只是互相发消息，而是围绕一个项目执行：

- 谁负责什么？
- 当前状态是什么？
- 阻塞在哪里？
- 证据链接是什么？
- 什么时候升级给人？

这里 Dashboard 很关键。

没有可视化，人很难长期信任 Agent 真的在工作。

### 多 AI API / Model Routing

多模型不是为了炫技。

真正有价值的是 model routing：

- 轻量扫描用便宜模型。
- 复杂推理用强模型。
- 代码任务用 coding model。
- 写作和总结用合适的语言模型。
- 高成本模型只在必要时使用。

这也是系统化的一部分：不是堆模型，而是把不同模型放到合适的位置。

### 我的踩坑

1. Agent 太多会增加协调成本。
2. 没有任务账本，多 Agent 会变成多窗口混乱。
3. Heartbeat 如果只检查不推进，就没有价值。
4. 没有 Project State，长对话会不断重复问已回答的问题。
5. 没有 Dashboard，人很难判断系统是否真的在推进。

### 特别 Tips

- 先一个主脑 + 一个专业 Agent，不要一开始搭十几个。
- 每个 Agent 要有边界和升级规则。
- 长项目必须维护 Project State。
- Dashboard 是信任层，不是装饰。
- 多 AI API 的价值在路由，不在数量。

### 金句

- 多 Agent 的价值不是数量，而是协作机制。
- Agent 不是聊天窗口，而是持续工作的角色。
- Dashboard 是信任层，不是装饰。

# 3. 三层落地方案：从工具变成系统（12–15 min）

刚才是肌肉展示，现在把它抽象成可复制的方案。

这套系统可以看成三层：

1. n8n / Airtable / Dashboard：流程层。
2. Skills：能力层。
3. Agent OS / MAE：协作层。

这三层不是平行工具，而是互相配合。

Agent 决定谁做、怎么推进。  
Skill 决定一类任务应该怎么做。  
n8n 决定状态怎么流转、怎么提醒、怎么进入看板。  
Dashboard 让人看见系统正在工作。  
Human Judgment 负责关键判断和边界。

---

## 3.1 流程层：n8n / Airtable / Dashboard

### 概念

流程层解决的是：事情如何被触发、如何流转、如何同步、如何可视化。

### 费曼解释

它像一个办公室里的传送带和公告板。

传送带负责把信息从一个地方送到另一个地方；公告板负责让大家知道现在事情到哪一步了。

### 适合做什么

- 定时提醒
- 状态同步
- 数据读取和写回
- 飞书 / 微信通知
- Dashboard 更新
- 失败告警

### 不适合做什么

- 不适合承载所有复杂判断。
- 不适合绕过人类确认做高风险动作。
- 不适合在没有状态设计时盲目自动化。

### 起步方法

先做一个最小闭环：

触发 → 读取表格 → 判断 → 通知 → 更新状态。

---

## 3.2 能力层：Skills

### 概念

能力层解决的是：同一类事情怎样被稳定复用。

### 费曼解释

Skill 就像菜谱。

不是每次做菜都重新发明，而是把材料、步骤、火候、成品标准写下来。

### 适合做什么

- 高频重复任务
- 有明确步骤和输出标准的任务
- 需要吸收外部参考的方法
- 需要长期优化的能力

### 不适合做什么

- 一次性任务不必急着 Skill 化。
- 没有真实产物验证的 Skill 很容易变成文档垃圾。

### 起步方法

做三次以上，再写 Skill。

一个最小 Skill 包含：

- 什么时候用
- 输入是什么
- 步骤是什么
- 输出标准是什么
- 常见坑是什么
- 如何记录反馈

---

## 3.3 协作层：Agent OS / MAE

### 概念

协作层解决的是：AI 如何有角色、有记忆、有任务、有升级机制地持续工作。

### 费曼解释

Agent OS 不是一个万能助手，而是一套小团队管理方式。

每个 Agent 有角色，任务有账本，项目有状态，系统会定期检查，搞不定就升级。

### 适合做什么

- 长任务
- 多步骤项目
- 多角色协作
- 需要持续跟踪的工作
- 需要沉淀知识资产的任务

### 不适合做什么

- 很小的一次性问题，不需要上 Agent OS。
- 边界不清楚时，不要贸然加很多 Agent。

### 起步方法

一个主脑 + 一个专业 Agent + memory + task ledger + Project State。

# 4. 顺序学习与逆序搭建（5–6 min）

## 讲稿

我自己的真实路径是：

n8n → Skill → Agent OS。

这个路径有一个好处：n8n 很直观，你能很快看到流程动起来。

但它也有一个问题：如果只从工具开始，很容易为了自动化而自动化。

你会搭很多 workflow，但不一定知道哪些工作真的值得自动化。

后来我发现，当我理解了 Agent OS 之后，再回头看 Skill 和 n8n，会清楚很多。

所以如果让我推荐别人，我会建议反过来：

Agent OS → Skills → n8n。

先想清楚：

- 我要让 AI 在哪些工作里持续协作？
- 哪些角色需要分工？
- 哪些任务会反复出现？
- 哪些经验值得沉淀成 Skill？
- 哪些状态值得自动化流转？

然后再搭 Skill 和 n8n。

这就是顺序学习和逆序搭建的区别。

## 金句

- 从工具往上拼，会很痛苦；从系统往下拆，会很清楚。
- 先理解操作系统，再安装能力模块，最后连接自动化流程。
- 不要为了自动化而自动化。

# 5. AI 时代的思考拆解：真正变化的是“从问题到方案”的路径（8–10 min）

这一段要从工具和架构，上升到个人能力。

AI 降低了执行成本，但提高了问题定义、系统拆解和产品判断的重要性。

---

## 5.1 项目反思 → 知识资产 / 书

### 讲稿

以前一个项目结束，可能写一篇复盘就结束了。

但现在可以做得更进一步。

一个项目结束后，我可以让 Agent 跨 session 总结：

- 这次项目有哪些关键决策？
- 哪些地方反复修改？
- 哪些问题是因为需求没说清？
- 哪些 Skill 用到了？
- 哪些模式下次还会出现？

然后把多个项目复盘串起来：

项目 A 的问题，项目 B 也出现了；
某类沟通问题重复出现；
某种产品判断可以沉淀成方法；
某个执行流程可以写成 Skill。

再进一步，它可以变成一本书、一套培训材料，或者一个新的 Skill。

这不是让 AI 瞎写一本书。

而是从真实项目经验里，把经验转成可学习资产。

### 金句

- 复盘不是终点，复盘可以变成知识资产。
- AI 让经验有机会跨项目、跨 session 被重新组织。

---

## 5.2 更积极地做软件 → 训练自己成为产品人

### 讲稿

第二个变化是，我会更积极地做软件。

过去做一个小产品，成本很高。

你要写代码、设计页面、接数据、部署、测试。

现在 AI 降低了代码成本，但这不代表产品变简单了。

相反，它让产品判断更重要。

因为当代码变便宜，真正稀缺的是：

- 你能不能定义问题？
- 能不能判断用户是谁？
- 能不能设计流程？
- 能不能验证结果？
- 能不能把 demo 变成可复用产品？

所以我现在把做软件当成训练产品能力的方法。

不是为了证明 AI 能写代码，而是训练自己从问题到产品方案、再到验证闭环的能力。

### 金句

- 代码比例下降，不代表技术能力下降，而是工作重心上移。
- 代码变便宜，产品判断变贵。
- 问题不是 AI 能不能写代码，而是你能不能设计让 AI 正确工作的系统。

---

## 5.3 内容生产 → 资产生产系统

### 讲稿

这次分享本身也是例子。

它不是“让 AI 写一篇稿”。

而是一个内容资产生产系统：

定位 → 状态收集 → 演讲稿 → HTML → 视频素材 → GitHub → Dashboard → 复盘。

最开始要判断：

- 观众是谁？
- 他们听完要相信什么？
- 哪些内容是肌肉展示？
- 哪些内容是方法论？
- 哪些内容适合视频？
- 哪些内容要变成资源 takeaway？

然后再拆成稿件、页面、视频、素材、状态和复盘。

所以内容生产不再只是写作，而是一套资产生产系统。

### 金句

- 内容不只是写稿，而是资产生产。
- 好的 AI 工作流，不只提高效率，也放大产品创意和审美创意。

---

# 6. 公司项目轻带：CER/PTR 是 proof，不是主线（4–5 min）

## 讲稿

前面讲的都是我的个人 AI 工作系统。

那它能不能落到公司复杂项目？

可以，但今天我只轻带一个 proof，不把它变成 CER 项目汇报。

比如 CER/PTR。

它不是简单让 AI 写文档，而是一个复杂流程：

输入材料、文档解析、模板映射、差异分析、文档生成、Evals、人工审核、平台运行、复用转移和 ROI。

这里 PLO 帮我的一个关键判断是：

不要直接按业务 Stage 拆开发模块。

Stage 是业务流程步骤。

开发更适合按能力包 / 交付包组织。

所以核心表达是：

代码结构按能力包，交付节奏按 E2E 闭环。

比如能力包可以是：

- 输入材料接收包
- 文档解析包
- 模板映射包
- 差异分析包
- 文档生成包
- Evals / QA 包
- 人工审核包
- 平台运行包
- 复用转移 / ROI 包

这个案例说明：个人 AI 工作系统不是玩具。

它可以帮助我把复杂公司项目拆成可管理、可验证、可复用的结构。

但公司项目必须注意边界：权限、合规、敏感数据、人审和责任归属。

## 金句

- 代码结构按能力包，交付节奏按 E2E 闭环。
- 个人 AI 工作系统不是玩具，它可以迁移到复杂公司项目。

# 7. 资源 Takeaway：别人可以怎么开始（6–8 min）

## 7.1 最小闭环

## 7.5 推荐起步路径

# 8. Closing（2–3 min）

## 讲稿

最后回到一开始的问题：AI 的能力边界在哪里？

我的当前答案是：边界不只取决于模型有多强，也取决于你有没有把它组织成系统。

如果 AI 只是聊天窗口，它解决的是一次问题。

如果它有 Skill，它开始能复用方法。

如果它有 Agent OS，它开始能持续协作。

如果它接入 n8n 和 Dashboard，它开始进入真实工作流。

这就是我现在正在搭的个人 AI 工作系统。

它还很早期，也有很多坑。

但我已经能看到一个方向：未来的高效工作，不一定是每个人拥有一个万能 Agent，而是每个人逐渐拥有一套适合自己的 AI 操作系统。

## 最后一句

不是用 AI 工具，而是设计一套让 AI 正确工作的系统。

# 9. Q&A 预备问题

## Q1. 这是不是太复杂了，普通人怎么开始？

回答：
不要一开始搭完整系统。先做一个最小闭环。比如一个任务提醒 workflow，一个可复用 Skill，一个主 Agent。系统是长出来的，不是一次搭完的。

## Q2. 多 Agent 会不会很乱？

回答：
会。如果没有角色边界、任务账本、状态表和升级机制，多 Agent 只会更乱。所以多 Agent 的价值不是数量，而是协作机制。

## Q3. 你现在是不是写代码变少了？

回答：
是，但这不代表技术能力下降，而是工作重心上移。过去重点是写代码，现在更重要的是定义问题、拆系统、验证结果和设计让 AI 正确工作的流程。

## Q4. 公司项目能不能这么做？

回答：
可以，但必须注意权限、合规、敏感数据、人审和责任归属。CER/PTR 这类项目适合用这种方法拆结构，但不能让 AI 绕过业务确认和合规要求。

## Q5. n8n / Skill / Agent OS 先学哪个？

回答：
我自己是 n8n → Skill → Agent OS，但如果重新搭，我建议 Agent OS → Skill → n8n。先理解角色和任务，再沉淀能力，最后自动化流程。
