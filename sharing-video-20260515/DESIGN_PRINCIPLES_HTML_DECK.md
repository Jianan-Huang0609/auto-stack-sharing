# 分享型 HTML Deck 设计原则 · 反思与沉淀

> 来自 Deck V6/V7 45min 分享「我如何搭了一个个人 AI 工作系统」的完整踩坑和迭代经验

---

## 一、最核心的认知：HTML Deck 的定位

### 它是什么
HTML Deck 是 **视觉证据层** + **结构引导层** + **带走物质层**。

### 它不是什么
- 不是讲稿的文字搬运工
- 不是 PPT 的 HTML 翻版
- 不是信息罗列的展示墙

### 黄金法则
```
你嘴上说的 ≠ 屏幕上放的
屏幕上放的 = 观众眼睛看到的证据
观众带走的 = 资源页 + 框架图 + 路径清单
```

## 二、页面类型的四象限

每一页先定位类型，再选模板：

| 类型 | 作用 | 模板 | 例子 |
|------|------|------|------|
| **证据页** | 展示真实产出 | Tab 切换 + 大图 | P03 实战展示 |
| **方法页** | 解释怎么做 | 左概念右案例 / 对比卡 | P18 n8n 流程层 |
| **流程页** | 展示步骤关系 | 横向节点链 / Pipeline | P12 Skill Pipeline |
| **过渡页** | 承上启下 | 标题 + 金句 + 视觉物 | P09 n8n→Skills 过渡 |

---

## 三、信息密度检查表

| 页类型 | 正文词数底线 | 必须有 | 禁止 |
|--------|-------------|--------|------|
| 证据页 | >20 | 至少一张大图 | 纯文字 |
| 方法页 | >40 | 概念 + 案例 + 反例 | 不看案例就能懂的纯理论 |
| 流程页 | >15 | 节点 + 箭头 + 每步一句话 | 超过 7 步 |
| 过渡页 | <20 | 一张视觉物 | 空页面 |

---

## 四、素材引用三定律

1. **一图一主**：同一张截图只能在一页当主角，禁止多页复用
2. **真实优先**：真实截图 > 模拟对话 > 占位文字。占位文字必须清掉
3. **用足资产**：assets 里有的素材一定要用，不要放着不用

## 五、交互模式排行榜

按用户反馈排序（从好到坏）：

| 排名 | 模式 | 用户评价 | 适用场景 |
|------|------|---------|---------|
| 🥇 | Tab 切换 + 大图展示 | "这个好，截图能看清楚" | 全量产物展示、多系统截图 |
| 🥈 | 左列表 + 右详情 | "信息组织得清楚" | 方法页、流程说明 |
| 🥉 | 对比卡（反例对照） | "知道什么对什么不对" | 质量证据、选择说明 |
| 4 | 时间线/进度链 | "爽，看到完整路径" | 学习路径、项目演进 |
| 5 | 三栏均分 | "截图太小，看不清" | 不推荐用于截图展示 |
| ❌ | 右侧圆点导航 | "不好用" | 已删除 |

## 六、图片展示的三个段位

| 段位 | 做法 | 问题 |
|------|------|------|
| 青铜 | `object-fit: cover` | 裁切严重，看不到完整内容 |
| 黄金 | `object-fit: contain` | 完整但太小（尤其竖长图） |
| 王者 | `overflow-y: auto` + `max-width: 85%` + 居中 | 完整可见、可滚动、视觉舒适 |

**结论**：凡是 Dashboard、App 截图、竖长图、多层表格图，一律用王者模式。

## 七、改一页的标准流程

```
1. 定类型 → 这页是证据/方法/流程/过渡？
2. 数词数 → 正文词数是够还是超？
3. 查素材 → assets 里有没有可用图？有没有被别的页用了？
4. 选模板 → 按四象限选模板
5. 写 HTML+CSS → 一个 script 内完成
6. 渲染截图验证 → headless Chrome 截图
7. git commit + push
```

## 八、容易犯的错（血的教训）

| 错误 | 后果 | 预防 |
|------|------|------|
| 把讲稿文字灌进 HTML | 页面变成字墙，观众不看 | 每页只放结构引导 + 证据 |
| 同一素材多页复用 | 观众疑惑"这图刚才不是看过了吗？" | 素材使用矩阵记录 |
| 没确认就删页面/图片 | 用户说"我什么时候说不要 X 了" | 先确认再删 |
| 改完没重新渲染验证 | 看起来改了实际上 layout 坏了 | 每次改完截图 |
| 默认用 cover 显示大图 | Dashboard 只显示左上角 | 先看图片尺寸再选 mode |
| 三栏均分放截图 | 每张图太小看不清 | 大图优先 |
| 改错页面（多页面编号相同） | 改了别的东西 | 确认 section 边界 |

## 十、结尾页铁律

1. **必须 callback 开头问题**：开头问的三个问题，结尾显式回答
2. **必须可带走**：资源包、路径清单、框架图，不能只有鸡汤
3. **必须让人知道怎么开始**：下一步行动清单，不是"加油你可以的"
4. **个人故事 > 通用建议**：我的路径远好于"你应该..."

## 十一、技术军规

### CSS
- 全部 inline style tag，不依赖外部 CSS 文件
- 变量统一在 `:root` 定义（颜色、圆角、阴影、mono/sans 字体）
- 网格布局：`grid-template-columns` > `flexbox` 用于页面结构
- 滚动：`scrollbar-width: thin` + `overflow-y: auto`

### JS
- 交互逻辑全部写在页面内的 `<script>` 中
- Tab 切换用 `dataset.mode` 控制 render 模式（cover/contain/scroll）
- 视频用 `<video autoplay muted loop playsinline>`

### 图片
- 优先 PNG（截图），JPG 用于照片
- 图片放 `assets/` 目录，命名规则：`{domain}-{thing}-{version}.png`
- 不要用外部 URL 图片（部署后可能失效）

## 十二、协作流程反思

### 这次暴露的问题
1. **Vercel 版本 ≠ 本地版本**：多次出现 Vercel 线上版和本地 git 不一致（因为其他人或其他 session 直接 push 了）。解决：每次改之前先 `curl` 获取线上版作为 ground truth。
2. **微信排队消息**：用户发多张图或者多条消息时，排队的消息没有上下文。解决：关键操作等用户确认后再动手。
3. **图片看不看得到**：DeepSeek 不能看图，切 GLM 才能看用户发的截图。但当用户发了图我需要看的时候才有价值切。
4. **push 超时**：大文件提交 + 网络慢 = SIGKILL。解决：分批 commit，减少单次 push 体积。

### 改进方向
- 每次改之前先 `curl` Vercel 线上版 → 以此为 ground truth
- 图片先看尺寸再决定用 cover/contain/scroll
- 修改后必须 screenshot 验证
- 小步提交，频繁 push
