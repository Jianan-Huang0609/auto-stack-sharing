## 0. 开场 Hook：先展现肌肉，不先讲理论（0:00–2:30）

### 讲法

我今天不想先讲概念。

我先给大家看几个东西：AI 现在已经能带我做什么。

第一，它可以帮我搭自动化流程。
比如 n8n 里，一个触发器进来，自动读取 Airtable 的任务状态，判断下一步，推送到飞书，最后同步到 Dashboard。
这个不是 demo 概念，而是工作系统里真实需要的闭环：任务有没有逾期、谁负责、有没有 blocker、是否要提醒人。

第二，它可以帮我做产品和内容资产。
比如这次分享本身：主题定位、结构、脚本、HTML 页面、视频分镜、Remotion 动画原型，都是 AI 参与生成和迭代的。

第三，它可以帮我写软件。
我现在不是只让 AI 写一段代码，而是用 Copilot / Codex 类工具，加上 Skill，把“需求 → 方案 → 开发 → 测试 → review → 发布”串起来。
这和普通 vibe coding 不一样，关键是它有规范、有验证、有复盘。

第四，它可以帮我搭 Agent 系统。
不是一个聊天窗口，而是多个有角色的 Agent：SAM、Andrew、Rex、Lulu、Alex。它们有记忆、有任务账本、有 heartbeat、有升级机制。

所以今天的分享，不是“我用了哪些工具”。
而是一个更具体的问题：

如果 AI 不只是回答问题，而是开始帮我推进项目、沉淀方法、搭系统，它的边界到底在哪里？

### 画面/素材

- n8n pipeline 动效：Trigger → Airtable → Code → Feishu → Dashboard
- AutoStackSharing HTML / 视频原型
- Copilot/Codex + repo 文件树
- Agent 框架图：SAM 居中，四个 Agent 环绕

### 屏幕金句

先看结果，再拆系统。
AI 不是一个工具，而是一套工作能力放大器。

## 1. 肌肉展示一：n8n — 把 AI 接进真实工作流（2:30–5:00）

### 讲法

第一块肌肉是 n8n。

很多人理解自动化，会觉得它只是“如果 A 发生，就做 B”。
但 n8n 真正有价值的地方，是它能把不同系统串起来：
触发器、数据库、代码判断、消息通知、看板同步。

我现在用它做几类事情：

1. 任务提醒：哪些任务逾期，哪些状态需要更新。
2. EOD 汇总：每天把 Agent 的工作状态整理出来。
3. Dashboard 同步：把 Airtable 里的任务状态变成可视化页面。
4. 分享项目跟踪：这次视频、素材、脚本、产物都可以进入任务流。

这里有一个特别实用的 tip：

n8n 不一定要全靠拖拽。很多时候，直接写 JSON 更快。
你可以让 AI 生成 workflow JSON，再导入 n8n，然后微调节点和 credential。
这会比手动一个节点一个节点搭快很多。

但踩坑也很明显：

第一，credential 和权限最容易卡住。
第二，workflow 一多，如果没有命名规范和状态表，很快会混乱。
第三，自动化不要一开始就追求全自动。最好先做半自动，让人确认关键节点。

### 概念

n8n 是 scale layer：负责触发、同步、通知、可视化。

### 优势

- 把 AI 输出接到真实系统里。
- 能和 Airtable、Feishu、Dashboard、Webhook 串起来。
- 适合做“状态变化”和“提醒”。

### 设置

- 用 Airtable 做任务状态源。
- 用 n8n 做 workflow 编排。
- 用 Dashboard 做可视化。
- 用 Feishu / WeChat 做人类通知入口。

### 踩坑

- credential 管理要清楚。
- workflow 要版本化，最好存 JSON 到 repo。
- 不要让自动化直接做高风险动作，先 dry-run 或人工确认。

### Tips

- 可以让 AI 直接写 n8n workflow JSON。
- Code 节点可以承担复杂判断，不必所有逻辑都拖节点。
- 每个 workflow 都应该有日志和失败路径。

## 2. 肌肉展示二：Copilot + Skill — 从写代码到写系统（5:00–8:00）

### 讲法

第二块肌肉是 Copilot / Codex 加 Skill。

单独用 AI 写代码，很容易变成“它写一段，我改一段”。
短期看很快，长期看会失控。

我现在更关心的是：
能不能把软件开发变成一套可重复流程？

比如一个开发任务，不是直接让 AI 写代码，而是：

先写 spec：到底要解决什么问题。
再写 plan：改哪些文件，风险是什么。
然后 build：让 AI 生成代码。
再 test：跑测试、截图、lint、build。
最后 review：检查是否符合目标，是否引入副作用。

这背后靠的不是一个 prompt，而是一组 Skills。

Skill 的价值是把“我怎么做一类事”沉淀下来。
比如：
产品生命周期编排 PLO、前端 slides、AI 视频生产、Feishu 写作、Airtable Dashboard、写书、复盘、模型路由、MAE autopilot。

特别重要的一点：Skill 可以自进化。
不是说让 AI 随便改自己，而是记录使用情况、用户反馈、重复问题。
同一个问题出现一次，只记录。
出现第二次，给 dry-run 建议。
出现第三次，再建议更新 Skill。
最后仍然由人确认。

更进一步，Skill 不是孤立的。
一个复杂任务可以串联十几个 Skill，形成一个体系。
比如这次分享：
PLO 判断任务类型 → frontend-slides 做页面 → ai-video-production-pack 做视频 → writing-book 沉淀长文 → airtable-dashboard 同步进度 → interaction-self-reflection 做复盘。

### 概念

Skill 是 capability layer：把一次经验变成可复用能力。

### 优势

- 减少重复 prompt。
- 让 AI 输出更稳定。
- 可以把复杂任务拆成可组合能力。
- 支持自我监控和渐进式优化。

### 设置

- 每个 Skill 有 SKILL.md：什么时候用、怎么做、输出标准。
- 复杂项目先走 PLO，决定任务类型和路线。
- 开发类任务走 spec → plan → build → test → review → ship。
- 重要反馈写回 Project State 和 memory。

### 踩坑

- Skill 太多会变成“技能垃圾堆”。需要健康检查。
- Skill 如果不绑定真实产物，容易变成说明书。
- 不要一开始就追求自动改 Skill，要先记录、观察、dry-run。

### Tips

- Skill 可以串联成 pipeline，而不是单点调用。
- Skill 可以记录反馈并自进化，但必须有人类确认。
- 越高频的任务越值得 Skill 化。
- 低频、一次性的任务不一定要做 Skill。

## 3. 肌肉展示三：Agent OS — 从一个 AI 到一个团队（8:00–11:00）

### 讲法

第三块肌肉是 Agent OS。

当任务越来越复杂，一个 AI 聊天窗口不够了。
因为真实工作里有不同类型的任务：研究、项目推进、内容设计、个人节奏、全局协调。

所以我搭了一个 Agent 框架：

SAM 是主脑，负责全局协调、任务编排、升级处理。
Andrew 负责学习、研究、技术评估。
Rex 负责工作项目、CER/PTR、工程推进。
Lulu 负责内容、写作、设计、视频。
Alex 负责个人节奏和生活支持。

Agent 的关键不是“人格化名字”，而是底层机制：

1. Memory：长期记忆，不让上下文丢失。
2. Task Ledger：任务账本，知道谁在做什么。
3. Heartbeat：定时检查，不靠人反复催。
4. Escalation：搞不定时升级给 SAM 或人。
5. A2A：Agent 之间可以互相通信。

这套东西继续往前，可以变成 MAE：Multi-Agent Execution。
也就是多个 Agent 不只是聊天，而是围绕一个项目执行、验证、同步、可视化。

这里的可视化很关键。
如果没有 Dashboard，人很难相信系统真的在工作。
所以 Agent OS 最好和 Airtable / Dashboard 接起来，让任务状态、证据链接、阻塞项都能看到。

它也可以接多 AI API。
不同模型适合不同任务：有的适合写作，有的适合代码，有的适合总结，有的便宜适合轻量扫描。
模型路由本身也可以变成一个 Skill。

### 概念

Agent OS 是 coordination layer：让多个 AI 角色围绕真实任务持续协作。

### 优势

- 任务有归属，不会散。
- 长任务可以跨 session 延续。
- Agent 可以分工，也可以升级。
- 结合 Dashboard 后，人能看到系统状态。

### 设置

- 每个 Agent 有 SOUL / USER / AGENTS / HEARTBEAT。
- 全局有 agent_tasks、daily brief、memory。
- SAM 负责跨 Agent 仲裁。
- 长任务默认同步 GitHub、Airtable、Dashboard。

### 踩坑

- Agent 太多会增加协调成本。
- 如果没有任务账本，多 Agent 会变成多窗口混乱。
- Heartbeat 不能只做检查，必须真的推动任务或发现阻塞。
- 需要明确哪些事必须人确认。

### Tips

- 先从一个主 Agent + 一个专业 Agent 开始，不要一上来十几个。
- 每个 Agent 必须有边界和升级规则。
- Dashboard 是信任层，不是装饰。
- 多 AI API 的价值在于路由，不是盲目堆模型。

## 4. 三层落地方案：从肌肉回到系统（11:00–13:00）

### 讲法

刚才展示的是三块肌肉：n8n、Skill、Agent。
现在把它们合在一起，就是我的三层落地方案。

第一层：n8n / Airtable / Dashboard。
它解决的是规模化和可视化：触发、同步、提醒、状态展示。

第二层：Skill。
它解决的是能力复用：把一次经验沉淀成下次可以稳定调用的方法。

第三层：Agent OS。
它解决的是持续协作：角色、记忆、任务、升级、heartbeat。

这三层不是平行工具，而是互相配合：

Agent 决定谁做、怎么推进。
Skill 决定一类任务应该怎么做。
n8n 决定状态怎么流转、怎么提醒、怎么展示。

如果只有 n8n，它只是流程自动化。
如果只有 Skill，它只是能力说明书。
如果只有 Agent，它可能还是聊天窗口。
三层合在一起，才开始接近一个 AI 工作操作系统。

### 屏幕金句

Agent 组织协作。
Skill 复用能力。
n8n 放大流程。
Dashboard 建立信任。
Human 保持判断。

## 5. 顺序学习与逆序学习（13:00–14:30）

### 讲法

这里有一个我自己的学习路径。

我实际上是顺序学的：
先学 n8n，因为它最直观，能立刻看到自动化流程。
然后学 Skill，因为我发现单次自动化不够，需要复用方法。
最后搭 Agent OS，因为任务复杂后，需要记忆、角色、升级和长期协作。

所以我的真实路径是：
n8n → Skill → Agent OS。

但如果让我给别人建议，我会反过来：
Agent OS → Skill → n8n。

为什么？

因为先有 Agent OS，你会知道任务和角色怎么分。
再有 Skill，你会知道哪些能力值得沉淀。
最后上 n8n，你才知道该自动化什么。

否则很容易陷入一个坑：
为了自动化而自动化，搭了很多 workflow，但没有真正解决重要问题。

### 屏幕文字

我的真实学习路径：n8n → Skill → Agent OS
推荐搭建路径：Agent OS → Skill → n8n

## 6. AI 时代的思考拆解：从问题到方案（14:30–17:30）

### 讲法

最后我想讲一点更底层的变化：AI 时代真正重要的能力，不是“会不会问 prompt”，而是能不能把问题拆成系统。

举几个真实的思考过程。

### 例子 1：项目反思如何变成一本书

以前做项目反思，可能是写一篇复盘文档。
现在可以更进一步。

一个项目结束后，我可以让 Agent 跨 session 总结：
这次项目有哪些决策？
哪些地方反复修改？
哪些 skill 用到了？
哪些问题下次还会出现？

然后把多个项目的复盘串起来：
按主题归类，按案例展开，按方法论提炼。

再进一步，它可以变成一本书的材料。
不是 AI 瞎写一本书，而是从真实项目经验里提炼结构。

这就是从“复盘文档”到“知识资产”的变化。

### 例子 2：更积极地做软件，训练自己为产品人

另一个变化是，我会更积极地做软件。

以前做一个小产品，成本很高：要写代码、设计页面、接数据、部署、测试。
现在 AI 降低了执行成本，但同时提高了产品判断的重要性。

因为当代码越来越便宜，真正稀缺的是：
你能不能定义问题？
能不能判断用户是谁？
能不能设计流程？
能不能验证结果？
能不能把一次 demo 变成可复用产品？

所以我现在把做软件当成训练产品能力的方法。
不是为了证明“AI 能写代码”，而是训练自己从问题到产品方案的完整路径。

### 例子 3：内容生产不再是写稿，而是系统生产

这次分享也是例子。

最开始不是写稿，而是确定：
观众是谁？
他们听完要相信什么？
我有哪些真实 proof？
哪些内容是肌肉展示？
哪些内容是方法论？
哪些内容需要视频呈现？

然后系统拆成：演讲剧本、视频剧本、素材清单、Remotion 动画、GitHub 状态、Dashboard 跟踪。

这不是“让 AI 写一篇稿”。
这是把内容生产变成项目。

### 屏幕金句

AI 时代，问题拆解能力变得更重要。
代码变便宜，产品判断变贵。
内容不只是写作，而是资产生产系统。

## 7. 最后 Takeaway：资源和可复制路径（17:30–20:00）

### 讲法

最后给大家几个可以带走的东西。

第一，不要从“我要用哪个工具”开始。
先问：我想让 AI 帮我持续推进哪类工作？

第二，从一个闭环开始。
比如：任务进入 → AI 判断 → 人确认 → 状态更新 → 复盘沉淀。
不要一开始追求全自动。

第三，把高频任务 Skill 化。
如果一类事情做三次以上，就值得沉淀成 Skill。

第四，把项目状态可视化。
没有 Dashboard 或任务账本，人很难长期信任 Agent。

第五，保留人的判断力。
AI 可以生成、总结、执行，但关键决策、风险动作、能力更新，最好仍然有人确认。

### 结尾

所以我今天真正想分享的不是一个工具栈。

而是一个判断：
AI 的能力边界，正在从“单次生成”扩展到“持续协作”。

但这个能力不会自动发生。
你需要把它组织起来：

用 Agent 承载角色，
用 Skill 沉淀能力，
用 n8n 串联流程，
用 Dashboard 建立信任，
用人类判断守住方向。

这就是我现在正在搭的个人 AI 工作操作系统。
