01 · Context

The Three Waves of AI Automation

过去半年对自动化的理解，经历了三次迭代。每次解决前一个问题，暴露新瓶颈。

WaveApproachSolvedNew Problem
1All-in on LLM chatNL as universal interfaceEvery task = new conversation
2All-in on n8n / DifyRepeatable workflowsComplex logic → spaghetti
3 (now)Layered by determinismRight tool per sub-taskRequires upfront design
Core insight

"Which tool is best?" is wrong. "How deterministic is this sub-task?" — that routes to the right path.

02 · Framework

Three Paths to Automation

Not one tool. Three paths — each with its own strengths, boundaries, and when to use it.

Path 1 · n8n / Dify

Deterministic pipelines. Event + fixed path. Flowchart drawn once, runs forever. cron, webhooks, data sync.

Path 2 · Skill + MCP

Crystallized expertise as reusable context. Every call = expert mode. Single-shot high-quality output.

Path 3 · Agent

Runtime decision engine. Each step depends on previous. Map drawn as you walk. LangGraph, CrewAI, custom harness.
03 · Path 1

n8n / Dify — Capability Boundaries

Strengths

  • Visual debugging — see what ran
  • 400+ native integrations
  • Zero-code cron + webhook triggers
  • Self-hosted = full data control

Limits

  • Complex logic → spaghetti flowcharts
  • No runtime decision-making
  • High-aesthetic output needs external tools
  • Visual programming ~50 node ceiling
Best for

Cron scraping, webhook processing, cross-system sync, notification routing. Fixed path = n8n.

04 · Path 2

Skill + MCP — Capability Boundaries

Strengths

  • Expert-quality output every time
  • Knowledge accumulates — skills evolve
  • MCP standardizes tool interfaces
  • Near-zero marginal cost per call

Limits

  • Requires upfront authoring investment
  • No runtime adaptability
  • MCP ecosystem maturing (auth, discovery)
  • Single-shot only — no multi-step planning
When MCP isn't needed yet

LLM platforms now natively handle filesystem, fetch, DB, GitHub. MCP adds a hop. Skip it until you hit cross-platform needs.

05 · Path 3

Agent Architecture — Capability Boundaries

Strengths

  • Handles open-ended, multi-turn tasks
  • Dynamic tool selection at runtime
  • Self-correct and retry
  • Orchestrates Path 1 + Path 2 as tools

Limits

  • Highest cost per task
  • Unpredictable — same input, different paths
  • Needs observability infrastructure
  • Overkill for deterministic workflows
The real distinction

"Multi-step" alone doesn't define an agent. n8n is multi-step too. Runtime decision-making is the defining trait.

11 · Tutorial

How I Built It

  1. Step 1: Install n8n (self-hosted via npm).Build one workflow: cron → GitHub API → Airtable. ~1 hour.
  2. Step 2: Write your first SKILL.md.Most frequent task. Encode best practices + output format. ~2 hours.
  3. Step 3: Connect a tool.Start with filesystem or Airtable. Teaches the tool protocol pattern. ~1 hour.
12 · Tutorial

How I Built It (continued)

  1. Step 4: Build a minimal agent harness.State machine + lock manager + LENS validator. Or use LangGraph. Wire to n8n + skills. ~4 hours.
  2. Step 5: Add observability.Structured logging with task_id. Feishu thread notifications. Airtable state ledger. ~2 hours.
Key lesson

Each step delivers standalone value. Don't build everything first — build layer 1, get value, add the next.

14 · Takeaways

What I Learned

  1. Determinism is the best router.Is this sub-task deterministic? — that answer routes to the right path.
  2. Skills compound. Workflows don't.Fixed path vs accumulated expertise. Invest in skills.
  3. Observability before intelligence.Feishu threads + Airtable state = free observability.
  4. Start ugly, refactor later.20-commit refactor came after knowing what patterns matter.
  5. LLMs should not validate LLMs.LENS gate catches 100% of evidence failures. Zero hallucination.
