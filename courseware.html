二 为什么需要分层？

从"一把梭"到"分层协作"——每个工程师都会经历的认知跃迁

第一波
💬

单次 LLM 对话

每次手动粘贴 prompt，结果用完即弃。能解决单点问题，但无法沉淀为可复用的能力。就像每次都手写一遍正则。

→
第二波
🔧

全塞进 n8n

试图用管道解决一切——包括需要审美判断、动态决策的任务。结果是 workflow 臃肿、JSON 配置失控、维护变成噩梦。

→
第三波
🧠

按确定性分层

确定性高的交给管道，需要 know-how 的交给 Skill，需要动态决策的交给 Agent。各司其职，边界清晰。

🔑 核心认知：不要把螺丝刀当锤子用。n8n 是确定性引擎，LLM 是判断力引擎——两者解决的问题维度不同。强行让 n8n 做"判断"，或者让 Agent 做"搬运"，都是低效的。分层不是多此一举，是让每种工具做它最擅长的那一件事。

给你一个任务，怎么判断用哪层？只问一个问题

「这个任务的确定性有多高？」

🔍 三个任务，走一遍判断流程

📡 任务 A：「每天早 9 点，抓取 3 个 RSS 源的新文章，筛选含"Agent"关键词的，推送到 Discord」
① 能提前画流程图吗？→ 能。步骤就是 cron → fetch → filter → push，路径一目了然。
② 直接判定：n8n。这个任务没有"判断"环节，没有"审美"需求，纯搬运。
→ 走 n8n
📊 任务 B：「做一份产品月报 PPT，包含数据图表 + 关键结论 + 下月计划」
① 能提前画流程图吗？→ 不能。月报结构涉及判断"哪些数据值得放、结论怎么措辞"，无法预设。
② 这是一次高质量"创作"吗？→ 是。输出 PPT 后不需要再跑第二步，任务边界清晰。
③ 直接判定：Skill。用 jianan-presentation-system skill 注入设计规范，一次生成 slide-by-slide 完整 PPT。
→ 走 Skill
⚙️ 任务 C：「把 Dashboard 从 Vue 2 迁移到 Vue 3，同时重构数据层，所有测试要过」
① 能提前画流程图吗？→ 不能。迁移过程中会遇到什么错误、哪些组件需要重写，都无法预知。
② 这是一次高质量"创作"吗？→ 不是。这不是"生成一个文件就完事"，需要多轮：改代码 → 跑测试 → 修 bug → 再改 → 再测。
③ 直接判定：Agent。需要边走边判断，每一步依赖上一步结果——这正是 Agent 的主场。
→ 走 Agent

📊 简单对照：这些任务走哪层？

这些任务走 n8n 这些任务走 Agent
定时 RSS 采集 → 推送到群 写一篇分析行业趋势的深度文章
Airtable ↔ Feishu 数据同步 设计一个新功能的技术方案
Webhook 收到事件 → 自动创建 issue 重构一个模块（多文件、多步骤）
每天汇总 GitHub stars → 发日报 排查一个随机出现的 bug
文件格式转换（JSON → CSV） 根据需求写代码 + 测试 + 部署
共同点：路径可预画，纯执行 共同点：过程需动态判断，不可预画
🧠 记住这个公式：路径确定 → n8n；路径不确定但一步到位 → Skill；路径不确定且需多步探索 → Agent。这就是分层决策的全部逻辑。

五 第一层：n8n / Dify — 确定性流程引擎

流程图画完就定了，路径预先可画

还记得刚才的判断公式吗？「能提前画流程图」的就是 n8n 的领域。这是最基础、最稳健的一层——像 CI/CD Pipeline 一样可靠。
核心概念：n8n = 你的个人 CI/CD Pipeline。定义好 DAG（有向无环图），之后完全自动运行。代码 push → 自动测试 → 自动部署，不需要每一步问人"要不要继续"。n8n 做的是完全相同的事：事件驱动、路径固定、全自动执行。

✅ 擅长什么 — 搬运工

Cron 定时任务：每周五 20:00 自动生成 overdue task 提醒
Webhook 响应：GitHub push → 自动同步到 Airtable
跨系统同步：Airtable ↔ Feishu ↔ GitHub 三向数据流通
通知分发：Gbrain 筛选后的高信号内容 → Discord + 飞书
内容采集：RSS / YouTube API / X API → 统一写入 Airtable

❌ 不擅长 — 需要判断力

审美判断："这张封面图好不好看？" 无法用 JSON 配置描述
内容质量评估："这篇文章值得深度读吗？" 需要语义理解
动态策略："第一步结果不理想，换一种方式重试" 路径不可预画
上下文推理："用户说的'那个项目'是指上周讨论的哪个？" 需要记忆

但 n8n 做不了一件事：创作。它能搬运数据、筛选数据、分发数据——但它不知道"什么是好的 PPT 设计"、"怎么写一段有冲击力的文案"。这时候就需要 Skill 层了 →

六 第二层：Skill — 领域知识胶囊

把最佳实践封装成上下文，每次调用都调出专家模式

n8n 擅长搬运，但不擅长创作 → 这时候需要 Skill。Skill 的本质是什么？把"我会怎么做"沉淀为"系统该怎么做"——就像设计团队的 Design System。
核心概念：Skill = AI 的 Design System。就像前端团队用一套组件库 + 设计规范保证视觉一致性，Skill 用一套 Markdown 规范（SKILL.md）保证 AI 每次输出的质量一致。你不需要每次都告诉 AI「用这个配色、这个字体、这个结构」——Skill 已经帮你记住了。

📦 JN-SkillHub — 四个真实 Skill

📊 jianan-presentation-system

PPT 视觉+内容+口述脚本一键生成。不是简单的 outline，而是完整的 slide-by-slide 设计——配色、排版、动画建议、演讲备注，全部打包输出。就像你把公司的 pitch deck 模板给了一个顶级设计师。

🎨 design-front

前端页面审美设计 skill。注入设计规范、配色方案、排版原则，让每次输出保持一致的审美水准。相当于把公司的 design system 文档喂给 AI，每次写前端代码都自动遵循设计规范。

✍️ impactable

内容表达力增强。把普通文案变成有冲击力的表达——不是改事实，而是强化呈现方式。就像有一个资深 copywriter 在旁边把关每段文案的语气和结构。

📚 codebase-to-course

代码库→结构化课程。自动分析代码结构，生成学习路径、知识点拆解和练习题目。新同事 on-boarding 时，直接把 repo 丢进去，输出一份可用的培训材料。

每次任务都是 Skill 的训练数据——经验不随项目结束而消散。就像每次 code review 的反馈都会变成团队的 best practice 文档。

但 Skill 做不了一件事：多步动态决策。如果需要「先试试方案 A，根据结果决定下一步」，Skill 的单次高质量输出模型就不够了。这时候，你需要 Agent →

七 第三层：Agent / CLI — 动态决策执行器

图一边跑一边画——每一步根据上一步结果决定下一步

Skill 擅长单次高质量输出，但做不了"跑到一半发现不对，换条路再跑" → Agent 就是为这种动态决策而生的。
核心概念：Agent = 你的 AI 同事。不是"你下指令它执行"，而是"你说目标，它自己规划步骤、选择工具、执行检查"。就像一个有经验的工程师接到任务——不是问你每一步该怎么做，而是自己去调研、尝试、修正。

🏢 你已经在用 Agent 了，只是没意识到

💻 VS Code + GitHub Copilot

这就是一个 L03 CLI Agent：
· Copilot Chat（Agent 分析）: "这段为什么慢？" → 分析代码，给出解释
· Copilot Edit（Agent 执行）: "重构这个函数" → 自动修改多行代码
· 人审确认（Human in the loop）: Agent 执行完，你来 review diff

Chat → Edit → Review 这个循环，就是 Agent 工作流的完整形态。 每次你在 Copilot Chat 里问问题、让它改代码，你就在使用 Agent。

🚀 Cursor Composer / Claude Code / Codex CLI

这些是"更进一步的 Agent"：
· 不只是补全一行代码
· 而是理解整个任务，自行规划步骤
· 创建文件、修改多处代码、运行测试
· 失败后自动调整策略重试

区别只是"自主程度"不同——从内联补全到全仓库重构，本质都是 Agent。 就像从 junior 到 senior：senior 不需要你告诉每一步细节。

✅ Agent 适合

· 深度长文写作：需要多轮推敲、改写、增删
· 复杂任务分解：先拆 → 逐一执行 → 汇总
· 多工具协同：查资料 → 写代码 → 测试 → 修 bug
· 代码工程：创建/修改文件，运行测试，git commit

❌ Agent 不适合

· 定时搬运：Agent 太贵、太快被轮询（cron 每 5 分钟调一次？烧钱）
· 纯格式转换：确定性操作不需要决策力
· 单次简单查询：浪费 Agent 的规划能力
· 高频小任务：每次决策的 token 开销不值得

⚙️ Jianan 的 Agent 实践 — Router + 双引擎 Fallback

架构：OpenClaw（编排层）→ MAE Router（智能路由）→ Codex / Claude CLI（执行层）

# 案例 1：结构化任务 → 自动路由到 Codex $ !mae code "创建 hello.py，用 argparse 接收参数" → Router: codex (任务类型=结构化代码) → Codex CLI: 19.5s, file created ✅ hello.py 已创建（argparse + 类型注解 + docstring） # 案例 2：创意任务 → 路由 Claude + 自动 fallback $ !mae code "设计一个 Agent 架构，包含路由和 fallback" → Router: claude (任务类型=架构设计/创意) → Codex failed ✗ → 自动重试 Claude → Claude CLI: 57s, 7,421 chars output ✅ 架构设计文档已生成，含路由逻辑和 fallback 机制
🔁 Fallback 机制的意义：单点 Agent 可能失败（超时、上下文不够、推理错误），Router + 双引擎 Fallback 让系统有了韧性。Codex 擅长结构化代码，Claude 擅长架构和创意——Router 根据任务类型智能选择引擎，失败了自动切换。这不是"万一坏了怎么办"的保险，而是架构设计中内置的容错层。
三层都讲完了。但最重要的不是每一层做什么——是它们怎么一起工作。单层是工具，三层协作才是操作系统 →

八 三层如何协作？

不是"今天用 n8n，明天用 Agent"——是同一个任务里三层同时工作

🔄 协作环路

🔌
n8n
触发 + 分发
→ 请求
🧠
Agent
决策 + 编排
→ 调用
💪

n8n 负责"何时做"（触发+分发），Agent 负责"做什么+怎么做"（决策+编排），Skill 负责"做成什么样"（执行+质量）——三者形成一个闭环。
🧬 类比：个人自动化操作系统 = 人体
🔌
n8n = 神经系统
自动化反射：感受到刺激（cron/事件）→ 自动响应。不需要思考，速度快、成本低。
🧠
Agent = 大脑
有意识决策：接收信息，分析判断，规划行动。消耗高但能处理复杂问题。
💪
Skill = 肌肉记忆
熟练动作模式：不需要重新学习，直接调取。一遍比一遍好，越用越强。

🎯 三层协作的三个真实场景

📊 场景 1：月报 PPT 自动生成
n8n ⏰ 每月1号触发 → Agent 🧠 分析本月数据，确定月报结构 → Skill 📐 按设计规范生成 slide-by-slide → n8n 📤 推送飞书
n8n 负责定时触发和最终交付，Agent 负责判断"本月重点是什么、怎么组织"，Skill 负责把判断转化为符合视觉规范的完整 PPT。
✍️ 场景 2：行业分析长文撰写
n8n 🔔 Discord 收到写作请求 → Agent 🧠 调研→大纲→初稿→修改→定稿 → Skill ✍️ impactable 润色表达力 → n8n 📤 发布到飞书 + 存入 Airtable
n8n 做输入输出的搬运，Agent 做深度写作（多轮推敲），Skill 保证最终输出的表达力达到标准线。
🎬 场景 3：自动化视频生产
n8n 📝 选题库 cron 触发 → Agent 🧠 生成/改写脚本 → n8n 🎙️ TTS→字幕→合成 → n8n 📤 推送飞书
n8n 串联整个 E2E 管线（TTS + 字幕 + 合成），Agent 只出现在最需要判断力的脚本生成环节——不浪费算力在确定性的格式转换上。
🎯 关键认知：三层不是"要么用这个要么用那个"——是同一任务的不同环节由不同层负责。n8n 串联流程，Agent 在关键决策点介入，Skill 在输出环节保证质量。这才是真正的"操作系统"——不同组件各司其职，形成一条完整的产线。

十 设计思路与关键决策

四个"为什么不"——理解架构取舍背后的原因

问题答案与权衡
为什么不是全塞进 n8n？ n8n 擅长确定性流程，但审美判断、内容质量评估、动态策略调整需要 LLM 的判断力。试图在 n8n 的 JSON 配置里描述"什么是好设计"——你会疯的。n8n 是执行引擎，不是判断引擎。
为什么不是全用 Agent？ Agent 每次决策都要消耗 token（💰贵）和推理时间（⏳慢）。定时的数据搬运、格式转换、通知推送这类任务，用 n8n 几乎零成本。让 Agent 做搬运工是对算力的浪费。就像你不会让架构师去手动部署服务器。
为什么 CLI 而不是 API？ CLI Agent 能写文件、改代码、执行 shell 命令、git commit——能做完整的工程闭环。纯 API 调用只能返回文本，无法直接操作文件系统。对于代码工程来说，CLI 是唯一能形成完整工作流的方式。
为什么是三层而不是两层？ 如果只有 n8n + Agent，中间缺了能力复用层。每次做 PPT 都要 Agent 从头想一遍设计规范？太浪费了。Skill 层就是沉淀——把成功经验封装为可复用的知识胶囊，让 Agent 调取而不是重新发明。
🎯 设计哲学：不是"哪个工具最好"，而是"哪类任务最适合哪个工具"。n8n 不是降级版的 Agent，Agent 也不是升级版的 n8n——它们解决的是不同维度的问题。一个健康的自动化体系，需要三个维度都覆盖。就像你不会用一个语言写所有代码——不同场景用不同工具，这不是妥协，是专业。

十一 Takeaways：从哪开始？

不是让你一步到位——三条渐进路径

1

先跑通一条 n8n workflow

比如：定时抓一个 RSS 源 → 筛选关键词 → 推送到群。感受"流程即代码"——定义好 DAG 之后完全自动运行，不需要人参与。这是最基础的自动化意识。就像你的第一个 CI/CD pipeline，跑通之后你会开始想"还有什么可以自动化？"

2

再封装一个 Skill

找一个你经常做的任务（周报模板？代码审查 checklist？），写一个 SKILL.md 文件描述你的最佳实践。下次让 AI 执行时引用它——你会惊讶于输出质量的提升。这就是"知识沉淀"的起点：把"我每次都要手动告诉 AI 的事"变成"AI 自动就知道的事"。

3

最后引入 Agent

当你有多个 n8n workflow 和几个成熟 Skill 后，让 Agent 来调度它们。告诉 Agent 目标，让它自己决定调用哪些工具、以什么顺序执行。这才是"动态决策"的真正价值——不是问 Agent"这一步怎么做"，而是告诉它"目标是什么，你自己想办法"。
